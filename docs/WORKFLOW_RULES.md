# قواعد العمل للمشروع

## 1. الهدف

هذا المشروع يعمل وفق نموذج Scrum-Light مع تركيز على تنظيم التطوير قبل التنفيذ. الهدف الرئيسي هو تقليل الأخطاء، توحيد العمل بين الفريق، وضمان أن كل مهمة واضحة وقابلة للتنفيذ ومراقبة.

## 2. مبدأ العمل

- لا تبدأ أي مهمة إلا بعد توضيح المطلوب بشكل واضح.
- كل طلب يجب أن يكون له صاحب مسؤول ومحدد.
- لا يوجد "تطوير بدون وثيقة" أو "تطوير بدون مراجعة".
- جميع التغييرات تذهب عبر Git branches + Pull Requests.
- أي تغيّر في قاعدة البيانات يجب أن يكون موثقًا قبل التنفيذ.
- أي تغيّر يهدّد الأمان أو البيانات يحتاج موافقة Tech Lead.

## 3. هيكل الفريق

### 3.1 Product Owner
- يحدد أولويات المشروع.
- يكتب متطلبات المستخدم أو User Stories.
- يوافق على Acceptance Criteria.

### 3.2 Tech Lead
- يراجع البنية التقنية.
- يقرّر اختيار الأدوات والتقنيات.
- يضمن توافق التنفيذ مع arquitectura العامة.
- يراجع القرارات الحرجة للأمان والبنية.

### 3.3 Backend Developer
- يبني APIs والـ Business Logic.
- يضمن سلامة البيانات وتوافق قواعد البيانات.
- يكتب tests للـ endpoints والـ services.

### 3.4 Frontend Developer
- ينفذ الواجهة حسب الـ design + API contract.
- يضمن تجربة المستخدم وسهولة الاستخدام.
- يقوم بالتحقق من حالات الخطأ والتحميل.

### 3.5 QA / Tester
- يكتب حالات الاختبار.
- يتأكد من أن كل feature يحقق الشروط المطلوبة.
- يراجع البقّع والاعطال قبل merge.

### 3.6 DevOps / Support
- إدارة البيئات (dev, staging, prod).
- إعداد Docker، CI/CD، الإشعارات، backup.
- متابعة الأداء والاستقرار.

## 4. نظام العمل

### 4.1 تقسيم المهام

يتم تقسيم المشروع إلى وحدات قابلة للتنفيذ، مثل:
- Tenant Routing
- Master DB Setup
- School DB Setup
- Children Module
- Guardians Module
- Fees Module
- Payments Module
- Authentication
- Dashboard UI

### 4.2 كل مهمة يجب أن تحتوي على:
- عنوان واضح
- الوصف
- النتيجة المطلوبة
- ملفات أو modules المتأثرة
- الخطوات التنفيذية
- معيار القبول
- نقطة مسؤولية

## 5. قواعد Git

### 5.1 Naming branches

يجب استخدام أسماء واضحة:
- feature/children-crud
- feature/fees-module
- fix/tenant-routing-bug
- chore/setup-postgres

### 5.2 Commit message

يجب أن يكون النموذج كما يلي:
- feat: add children registration API
- fix: resolve tenant subdomain middleware bug
- docs: add team workflow rules
- chore: setup postgres docker config

### 5.3 Pull Request Rules

قبل merge:
- يجب أن يكون هناك review من عضو آخر على الأقل.
- يجب أن تمر جميع الاختبارات.
- يجب أن يكون هناك description واضح للـ change.
- لا يمر PR إلا إذا كان مطابقًا لمعايير الجودة.

## 6. قواعد البرمجة

### 6.1 Naming
- أسماء المتغيرات واضحة ووصفية.
- لا تستخدم أسماء مختصرة غير واضحة.
- أسماء الـ modules، الـ services، الـ controllers توضح المهمة.

### 6.2 Architecture
- كل module له مسؤولية واحدة فقط.
- لا تخلط بين منطق العمل ومنطق الـ controller.
- لا تكتب منطق أعمال داخل الـ controller مباشرة.

### 6.3 Error handling
- كل API يجب أن يرجع رسائل خطأ واضحة.
- لا تترك try/catch فارغًا.
- تسجيل الأخطاء (logging) يكون مطلوبًا في الحالات المهمة.

### 6.4 Security
- لا تترك بيانات حساسة داخل الكود.
- لا يتم حفظ الأسرار في repository بشكل مباشر.
- كل endpoint يجب أن يراجع صلاحية المستخدم.

## 7. قواعد قاعدة البيانات

- لا يتم تعديل schema بدون مراجعة.
- أي migration يجب أن يكون موثقًا في ملف مستقل.
- لا تكتب SQL داخل التطبيق بطريقة غير منظمة.
- يجب حفظ schema version لكل مدرسة عند تحديثها.
- كل تغيير في العلاقة بين الجداول يحتاج توثيق.

## 8. قواعد الاختبار

- كل feature أساسي يحتاج test واحد على الأقل.
- لكل API مهم يجب اختبار:
  - النجاح
  - الخطأ
  - صلاحيات الوصول
  - الحالات الحدية

### الحد الأدنى المطلوب
- Unit tests للـ services المهمة
- Integration tests لبعض الـ endpoints
- Manual QA قبل التقديم النهائي

## 9. مراجعة الكود

- يتم مراجعة الـ PR من قبل عضو مختلف عن المبرمج.
- يجب أن يركز reviewer على:
  - جودة المنطق
  - وضوح الكود
  - الأمان
  - الأداء
  - التوافق مع القواعد المعمارية

## 10. Definition of Done

المهمة تعتبر مكتملة فقط إذا:
- تم تنفيذها بالكامل
- تم اختبارها
- تم التحقق من القبول
- تم review الكود
- تم تحديث الوثائق إن لزم
- تم التأكد من عدم تأثيرها على الأنظمة الأخرى

## 11. قاعدة العمل اليومية

- سيتم تقسيم المهام في Jira / Trello / GitHub Projects
- كل يوم يبدأ بـ update قصير للفريق
- لا يتم إدخال task جديد إلا بعد إنهاء السابق أو إحالته لمراجعة
- أي مشكلة تقنية حرجة يتم توثيقها ومناقشتها قبل اتخاذ قرار

## 12. تقارير التقدم

يجب تحديث الحالة أسبوعيًا على الأقل:
- Done
- In Progress
- Blocked
- Next

## 13. سياسة التوثيق

كل قسم مهم يجب أن يكون له:
- README أو Documentation
- API contract أو description
- تفاصيل تجريبية إن لزم

## 14. القاعدة الذهبية

لا شيء يُنشأ بشكل عشوائي. كل خيار فني أو تصميمي يجب أن يكون مستندًا، موثقًا، ومُراجعًا قبل التنفيذ.
