# هيكل المشروع الأساسي

## 1. الهدف

هذا المشروع يهدف إلى بناء نظام SaaS لإدارة المدارس ورياض الأطفال، مع بنية متعددة المستأجرين (multi-tenant) ومفصولة حسب المدرسة، مع الحفاظ على نسخة تطبيق واحدة فقط وتغيير قاعدة البيانات حسب subdomain.

## 3. شرح كل قسم

### apps/api
- التطبيق الرئيسي للـ Backend
- مسؤول عن APIs، authentication، tenant routing، business logic
- سيتم بناءه على NestJS في المراحل القادمة

### apps/web
- واجهة المستخدم الإدارية للمدارس
- صفحات تسجيل الأطفال، الرسوم، الطلاب، الرعاية، واللوحة الرئيسية
- سيتم بناءه لاحقًا باستخدام React + TypeScript

### packages/shared
- ملفات مشتركة بين frontend و backend
- أنواع البيانات، القيم الثابتة، utilities، interfaces
- الهدف: تقليل التكرار وتوحيد المصطلحات

### docker
- إعدادات الحاويات مثل PostgreSQL و Redis و PgBouncer
- يحافظ على بيئة التطوير موحدة للجميع

### docs
- وثائق المشروع، القواعد، الأدوار، الخطة، والاشتراطات التشغيلية

## 4. المرحلة الحالية

نركز في هذه المرحلة على:
- هيكل المشروع
- إعداد الوثائق
- توزيع المهام داخل الفريق
- تعريف بنية Master DB + School DB
- تجهيز خطة التنفيذ للمرحلة الأولى

## 5. تقسيم المهام داخل الفريق

### 1) Team Lead / Tech Lead
- الموافقة النهائية على البنية التقنية
- متابعة التنفيذ عبر المراحل
- مراجعة التحديات التقنية
- تحديد أولويات التطوير

### 2) Backend Developer
- بناء APIs
- إدارة قاعدة البيانات
- تصميم tenant-aware architecture
- إدارة migrations

### 3) Frontend Developer
- تصميم واجهات الإدارة
- بناء صفحات تسجيل الأطفال والرسوم
- ربط الواجهة مع الـ API

### 4) QA / Tester
- كتابة حالات الاختبار
- التحقق من قبول المتطلبات
- فحص الأخطاء قبل الدمج

### 5) DevOps / Infrastructure
- تجهيز Docker
- PostgreSQL
- CI/CD
- البيئات مثل dev و staging

### 6) Product Owner / Stakeholder
- تحديد المتطلبات
- مراجعة النتائج
- إعطاء الأولوية للمستجدات

## 6. توزيع العمل حسب المراحل

### المرحلة 1: Foundation
- Tech Lead: تصميم البنية والقرارات التقنية
- Backend Developer: Master DB + tenant routing
- DevOps: Docker و PostgreSQL
- QA: مراجعة أولية للبيئة وملاءمة القواعد

### المرحلة 2: Children + Fees
- Backend Developer: APIs الأطفال والرسوم
- Frontend Developer: صفحات التسجيل والرسوم
- QA: اختبار السيناريوهات الأساسية

### المرحلة 3: Admin + Reports
- Backend Developer: تقارير وتقسيم الصلاحيات
- Frontend Developer: لوحة الإدارة
- QA: اختبار الأداء والوظائف

## 7. قواعد العمل الأساسية

1. لا تبدأ أي مهمة بدون توضيح واضح
2. كل مهمة لها صاحب مسؤول
3. كل تغيير مهم يكتب في الوثائق
4. لا يتم الدمج إلا بعد مراجعة
5. كل مرحلة لها معيار قبول واضح
6. يتم توثيق أي مشكلة تقنية أو تأخير

## 8. Definition of Ready و Definition of Done

### Definition of Ready
- الوصف واضح
- النتيجة المتوقعة محددة
- المسؤول معروف
- القيم/المتغيرات والبيئة واضحة

### Definition of Done
- تم تنفيذ المهمة بالكامل
- تم مراجعة الكود أو الوثيقة
- تم التحقق من النتيجة
- تم تحديث الوثائق إذا لزم
- تمّ الاتفاق على قبولها من صاحب المهمة

## 9. قاعدة التصميم الأساسية

- التطبيق الأساسي واحد
- كل مدرسة لديها قاعدة بيانات مستقلة
- تحديد المدرسة عبر subdomain
- لا يتم تطوير أي ميزة جديدة دون توثيقها أولًا
- لا يتم تعديل البنية أو قاعدة البيانات بدون مراجعة فنية

## 10. الخلاصة

هذا الهيكل يمثل نقطة البداية الرسمية للمشروع، ويعمل كقاعدة موحدة لتوزيع المهام، تنظيم العمل، وضبط المرحلة الحالية قبل بدء التطوير الفعلي.
